## A. 【設計・対応済み】番号札モード OFF の注文が、誰の確認も通らずに「支払い済み」で確定する

**直す前の挙動**

札モード OFF で確定した注文は `status=completed` + `paid=true` で生成される。結果:

| 画面 | 出るか |
|---|---|
| 厨房（焼き待ち） | **出ない**（`pending` のみ表示） |
| 受渡 | **出ない**（`ready` のみ表示） |
| 支払い口・未払い欄 | **出ない**（`paid=true` のため） |
| 支払い口・支払い済み欄 | 出る（ただし記録であって操作待ちではない） |
| 記録表・売上 | 出る |

**何が問題か**

札モード ON 側には「未払いのまま渡そうとすると確認ダイアログ」「支払い口に未収が積まれる」
「取りはぐれ額が赤字で出る」という三重の網がある。OFF 側には **一つもない**。

受付係が現金を受け取り忘れても、システムは最初から「支払い済み」として記録する。
差額は締めまで誰も気づけず、締めても「受注額 = 受取済み」で一致するので気づけない。

**現金の受取を確認する画面もない**。確定すると `showThanks` が合計金額を出すが、
3.5 秒で自動的に閉じる（`app.js:620`）。「N 円お預かりしました」のような確認手順はない。

**運用上の想定と、実際にやりたいことのズレ**

いまの作りは「作り置きがあるので、その場で渡して受付で現金を受け取る」を前提に
最短経路にしてある。だが番号札を使わないことと、厨房・受渡・支払い口を通さないことは
本来別の話で、いまは `useTags` 一つに縛られている。

**直した内容**

- `BuildOrder` は札なしの注文を `completed` ではなく **`ready`** で立てる。
  飛ばすのは厨房だけで、受渡と支払いは通常の注文と同じ経路を通る。
- 受付は `paid` を常に `false` で渡す。代金は誰かが一度押して初めて記録される。
- 札が無い注文は画面に `受付12` のように受付順を出す（`numOf`）。
  これが無いと受渡口と支払い口で「どの注文か」を口頭で確かめるしかない。
- `database.rules.json` の作成時の状態を `pending|ready` に変えた
  （`completed` では作れない）。ルールの版を v6 に上げてある。
- 受渡の画面に**着信音**を足した。札なしの注文は厨房を通らないので、
  これが無いと受渡口に何の合図も出ない。

対応するテスト: `TestBuildOrderImmediate` / `TestRulesCreatableStatuses` /
`tag_contract_test.mjs` の [3] / `pure_parity_test.mjs`。

## B. 【バグ・対応済み】記録表の「支払い受取」ボタンが、お客様側の金額表示を無言で乗っ取る

**直す前の経路**

1. `renderRows()` が記録表の各行に `data-act="pay"` のボタンを描く（`app.js:1164`）
2. グローバルのクリックハンドラが `case 'pay': openCollect(id, false)`（`app.js:1392`）
3. `openCollect()` が `showAmount(o)` を呼び、`display/payment/<口>` に金額を書く（`app.js:1266`）
4. 続けて `renderPay()` を呼ぶが、**いま開いているのは記録表タブなので何も見えない**

**結果**

- お客様に向けた金額表示の端末に、誰も操作していない注文の金額が出る
- 出しっぱなしになる。記録表タブには「確認した」「戻る」のボタンが無いので消せない
- 押した本人の画面では何も起きないので、押し間違いにも気づけない
- `collecting` が埋まるため、支払い口タブで別の注文を会計しようとすると干渉する

支払い口タブの `openCollect` には「やめたら必ず消す」設計が入っている
（`cancelCollect` / `confirmCollect` が `clearAmount()` を呼ぶ）。
記録表からの経路だけがその外に出ている。

**直した内容**

記録表のボタンを `data-act="takepaid"` に分け、`setPaid(id, true)` を直接呼ぶ。
客側の画面には一切触れない。`openCollect` は支払い口タブからのみ使う。

## C. 【バグ・対応済み】営業回の締めで、CSV が保存されないまま切り替わることがある

**直す前の経路**

```js
onYes: async ()=>{
  saveCSV('orders'); saveCSV('summary');   // ← 戻り値を見ていない
  ...
  await set(ref(db,'config/session'), id);
  toast(`新しい営業回 ${id} を始めました。`, 'info');
}
```

`saveCSV()` は WASM が未準備なら **何も保存せずに `false` を返す**（`app.js:1580`）。
戻り値を見ていないので、保存できていなくても営業回はそのまま切り替わる。

さらに `saveCSV` が出す「集計モジュールの準備ができていません」のトーストは、
直後の「新しい営業回を始めました」で**上書きされて消える**（→ 問題 D）。

注文自体は DB に残るので記録が消えるわけではないが、
ダイアログが「今の回のCSVを保存してから切り替えます」と約束している以上、
これは約束を守れていない。

**直した内容**

- 締める前に `csvReady()` で確かめる。作れないなら**営業回を切り替えず**、
  理由を 9 秒出す（「営業回はまだ切り替えていません」と明記）。
- 2 枚目以降も戻り値を見て、失敗したらそこで止める。
- ダウンロードの 2 連発の間に 800ms 置いた。連続した programmatic download の
  2 枚目を落とさない端末があるため。**これは実機で確かめていない**。
  iPad で運用するなら一度試すこと。

## I. 【バグ・対応済み】支払い口の金額表示が毎回失敗する（`nowServer` のスコープ）

**症状**

支払い口で注文を選ぶと必ず
「お客様側の画面に金額を出せませんでした：nowServer is not defined」
が出る。お客様側の端末には一度も金額が出ていなかった。

**直す前の経路**

1. 金額表示の節（`AMOUNT_HOLD_MS` / `amountShown` / `amountTimer` / `serverSkew` /
   `nowServer` / `renderAmount`）が `authReady.then(()=>{ … })` の**内側**にあった
2. `showAmount()` / `clearAmount()` はモジュール直下にある
3. `at: nowServer()` を評価した瞬間に `ReferenceError`
4. `try` の `catch` が `writeHint()` に渡すので、**書き込みの失敗の形で出る**

**何がたちが悪いか**

- 文言が「出せませんでした」なので、原因がルール・認証・通信の側にあるように読める。
  実際にこの症状は 4 回起きている「公開されているルールが古い」と見分けが付かない
  （そちらは `rulesVersion` の赤い帯で切り分けられるが、こちらは帯が出ない）
- 注文の確定と支払いの記録は同じ `set` / `runTransaction` で通るので、
  「DB は生きているのに金額だけ通らない」に見える
- `clearAmount()` も同じ理由で常に失敗していた。こちらは `console.error` だけなので
  気づけない。ルールが通る状態なら**一度出た金額が消えない**経路でもあった
  （B で直したはずの「出しっぱなし」が、別の理由で復活していた）

**直した内容**

- 状態と `renderAmount()` をモジュール直下へ出した。
- 購読は `authReady.then` の中に残した。`display/payment` は `auth != null` を要求し、
  `PERMISSION_DENIED` で切られた購読は自動では戻らない。

対応するテスト: `dom_wiring_test.mjs` の [8]。
`authReady.then` の中で宣言したものをブロックの外から参照していたら落ちる
（修正前の `app.js` に当てると `nowServer` を名指しで落ちる）。

## J. 【バグ・対応済み】ステッパーがカードの枠からはみ出す（`min-height:0`）

**症状**

iPad 横向きの受付画面で、ステッパー（−／＋の帯）がカードの下枠を突き抜ける。
カードの枠線がステッパーの真ん中を横切る形で出る。実機の画面写真で約 50px。

**直す前の指定**

```css
@media (orientation:landscape) and (min-width:700px) and (max-height:1120px){
  .item{ … ; min-height:0}
}
```

グリッドの行は通常「中身より小さくならない」下限を持つ。`min-height:0` はその
下限を 0 に落とす。高さが足りないとき、行はカードの中身を無視して縮み、
**カードの箱だけが潰れる**。中身のステッパー（ボタン 44〜60px ＋余白）は
これ以上縮めないので、潰れた枠の外へ出る。

`min-height:0` は「flex/grid の子が縮まないときに置く」定石だが、
**縮める中身を持たないカードに置くと逆に働く**。

**直した内容**

- `.item` を既定（`min-height:auto`＝中身を下限にする）に戻した。
  カードは中身より小さくならない。
- `.menu{overflow-y:auto}` を足した。本当に高さが足りないときは、枠を破る
  のではなくメニュー側が送られる（確定ボタンは画面に残る）。

**その後（高さの配分を組み直した）**

上の `overflow-y` が実機で前に出てしまい、「合計の行が動かないままカードだけ
送られる」状態になった。最後の砦は残したまま、働かなくて済むようにした。

- `#view-order` の `justify-content:center` をやめ、`.menu{flex:1}` にした。
  余った高さは画面の上下に散らさず、全部カードに渡す。
  中央寄せのままだと、カードは中身ちょうどで窮屈なのに余白だけが端に溜まる。
- `.item{justify-content:space-between}` ＋ `.item-head{flex:1}`。
  背が高くなったぶんの余白をカードの底に溜めず、説明文の上下に散らす
  （`space-between` だけだと真ん中に穴が空く）。
- 表札・合計の数字・数え札の行を少しずつ詰め、空いたぶんをカードへ回した。
- `.order-top` `.total-row` `.tally` `.cta-row` を `flex:none` にした。
  縮むと中身がはみ出す側なので、縮ませない。

**確認できていないこと**

手元の Chrome では、実機と同じ 1180×796・同じフォントでも再現しない。
WebKit 側だけで出る挙動と思われる。余裕があるときの描画が修正前と
**画素単位で同一**であることは確認済み（＝通常時に何も変えない）。
実機での最終確認が要る。

## K. 【バグ・対応済み】iPad で通知音が鳴らない

**3 つ重なっていた**

1. **消音スイッチ。** iOS の消音は Web Audio だけを黙らせる（`<audio>` や動画は鳴る）。
   端末の音量を上げても直らないので原因に辿り着けない。
   → `navigator.audioSession.type = 'playback'` を宣言し、対象から外した。

2. **最初の 1 回が必ず無音。** `unlock()` の直後に鳴らしていたが、iOS の
   `resume()` は非同期。戻る前に組み立てるので `live()` が false になり捨てられる。
   → `play()` を挟み、context が起きてから鳴らす。

3. **1 回失敗すると二度と試さない。** 解錠の購読が `{once:true}` だった。
   iOS は他アプリへ移る・画面を消す・通話が入ると context を止めるので、
   一度止まると戻らない。
   → 起きるまで（止まったらまた）試す。`visibilitychange` でも起こす。

**構造的な問題（これが本命）**

iOS は**一度も触られていない端末では音を出せない**。厨房・呼び出し表示・金額表示は
設計上**誰も触らない端末**なので、注文が来ても永久に鳴らない。
しかも鳴らない理由が画面のどこにも出ないため、気づけない。

→ 音が止まっている間だけ「タップして音を出す」ボタンを左下に出す（`#audio-wake`）。
押す操作そのものが iOS の解錠条件を満たす。押しても消えない場合は
context が起動できていないということなので、切り分けにも使える。

**Render は無関係。** 応答ヘッダに `Permissions-Policy` / `Feature-Policy` /
`CSP` / `Cross-Origin-*` は 1 つも無い。Web Audio は配信元に依存しない。

## D. 【バグ】トーストが 1 個しかなく、後から出たものが前を消す

`toast()` は `$('toast')` という **単一要素**の `textContent` を上書きする（`app.js:119`）。

- エラーを出した直後に成功メッセージを出すと、**エラーが読まれる前に消える**（→ 問題 C が実際にこれ）
- 「戻す」ボタン付きのトースト（厨房の「用意した」）も、次のトーストが来た瞬間に
  ボタンごと消える。**押し間違いを取り消す唯一の導線が、無関係な通知で失われる**
- `clearTimeout(toastT)` で前のタイマーも消えるので、2 件目の表示時間だけが効く

厨房は「用意した」を連打する画面なので、2 件続けて押すと 1 件目の「戻す」は必ず消える。

## E. 【設計】営業回を切り替えると、在庫が満タンに戻ったことになる

**確認した計算**

- `remainingOf` = `stock`（`config/limits/stock` の固定値）− `soldOf`（**いまの営業回だけ**を集計）
- 営業回を切り替えると `soldOf` が 0 になる → `remaining` が `stock` に戻る

物理的な在庫は 1 個も戻っていないのに、画面は「この先あと 100 カップ売れます」と言う。
厨房の焼き足し判断もこの数字を見ている。

確認ダイアログには「売上・在庫・番号札の集計が 0 から始まります」とあるが、
これを「在庫が満タン扱いに戻る」と読み取れる人は少ない。
午前の部 → 午後の部のような使い方をすると、そのまま売り切れ検知が効かなくなる。

**直すなら**: 営業回の切替時に在庫を入力し直させる、または `stock` を営業回ごとに持つ。

## G. 【設計】番号札の重複と在庫の二重引き当ては、クライアント側でしか防いでいない

これはコード中のコメントで既に自覚・許容されている（`app.js:541`）ので新発見ではないが、
場合分けの一覧としては挙げておく。

`placeOrder` は確定直前にサーバーの現在値を読み直して窓を縮めているが、
**読んでから書くまでの間は残る**。受付が 2 台あると、
「最後の 1 カップを両方が売る」「同じ札を両方が出す」が原理的に起こりうる。

`database.rules.json` 側にも札の重複を止める規則はない（RTDB のルールでは書きにくい）。

コメントは「文化祭の規模では窓を縮めるほうが割に合う」と判断理由まで書いてあるので、
**このまま行くなら、起きたときの直し方**（記録表から中止 → 取り直す）を
運用手順に書いておくのが現実的。
