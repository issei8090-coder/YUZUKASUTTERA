テストは Go / Node とも全部通っている（2026-09-30 時点）。
つまり以下はテストで捕まらない種類の問題。

重い順。

## A. 【設計】番号札モード OFF の注文が、誰の確認も通らずに「支払い済み」で確定する

**現状**（`app.js:594` / `order.go:840` 付近）

札モード OFF で確定した注文は `status=completed` + `paid=true` で生成される。結果:

| 画面 | 出るか |
|---|---|
| 厨房（焼き待ち） | **出ない**（`pending` のみ表示） |
| 受渡 | **出ない**（`ready` のみ表示） |
| 支払い口・未払い欄 | **出ない**（`paid=true` のため） |
| 支払い口・支払い済み欄 | 出る（ただし記録であって操作待ちではない） |
| 記録表・売上 | 出る |

**何が問題か**

札モード ON 側には「未払いのまま渡そうとすると確認ダイアログ」「支払い口に未収が積まれる」
「取りはぐれ額が赤字で出る」という三重の網がある。OFF 側には **一つもない**。

受付係が現金を受け取り忘れても、システムは最初から「支払い済み」として記録する。
差額は締めまで誰も気づけず、締めても「受注額 = 受取済み」で一致するので気づけない。

**現金の受取を確認する画面もない**。確定すると `showThanks` が合計金額を出すが、
3.5 秒で自動的に閉じる（`app.js:620`）。「N 円お預かりしました」のような確認手順はない。

**運用上の想定と、実際にやりたいことのズレ**

いまの作りは「作り置きがあるので、その場で渡して受付で現金を受け取る」を前提に
最短経路にしてある。だが番号札を使わないことと、厨房・受渡・支払い口を通さないことは
本来別の話で、いまは `useTags` 一つに縛られている。

**直すなら**

`useTags`（札を配るか）と、通る工程（厨房 / 受渡 / 支払い）を分離する。
少なくとも `paid` を自動で `true` にするのはやめ、受付で現金を受け取ったことを
一度は押させる。

## B. 【バグ】記録表の「支払い受取」ボタンが、お客様側の金額表示を無言で乗っ取る

**確認した経路**

1. `renderRows()` が記録表の各行に `data-act="pay"` のボタンを描く（`app.js:1164`）
2. グローバルのクリックハンドラが `case 'pay': openCollect(id, false)`（`app.js:1392`）
3. `openCollect()` が `showAmount(o)` を呼び、`display/payment/<口>` に金額を書く（`app.js:1266`）
4. 続けて `renderPay()` を呼ぶが、**いま開いているのは記録表タブなので何も見えない**

**結果**

- お客様に向けた金額表示の端末に、誰も操作していない注文の金額が出る
- 出しっぱなしになる。記録表タブには「確認した」「戻る」のボタンが無いので消せない
- 押した本人の画面では何も起きないので、押し間違いにも気づけない
- `collecting` が埋まるため、支払い口タブで別の注文を会計しようとすると干渉する

支払い口タブの `openCollect` には「やめたら必ず消す」設計が入っている
（`cancelCollect` / `confirmCollect` が `clearAmount()` を呼ぶ）。
記録表からの経路だけがその外に出ている。

**直すなら**

記録表の「支払い受取」は `openCollect` ではなく `setPaid(id, true)` を直接呼ぶ
（客側表示を経由する必要がない）。または押したら支払い口タブへ移す。

## C. 【バグ】営業回の締めで、CSV が保存されないまま切り替わることがある

**確認した経路**（`app.js:1451`）

```js
onYes: async ()=>{
  saveCSV('orders'); saveCSV('summary');   // ← 戻り値を見ていない
  ...
  await set(ref(db,'config/session'), id);
  toast(`新しい営業回 ${id} を始めました。`, 'info');
}
```

`saveCSV()` は WASM が未準備なら **何も保存せずに `false` を返す**（`app.js:1580`）。
戻り値を見ていないので、保存できていなくても営業回はそのまま切り替わる。

さらに `saveCSV` が出す「集計モジュールの準備ができていません」のトーストは、
直後の「新しい営業回を始めました」で**上書きされて消える**（→ 問題 D）。

注文自体は DB に残るので記録が消えるわけではないが、
ダイアログが「今の回のCSVを保存してから切り替えます」と約束している以上、
これは約束を守れていない。

**副次的な問題（未確認・要実機検証）**: `a.click()` によるダウンロードを 2 連発している。
Safari / iOS は連続した programmatic download の 2 回目をブロックすることがある。
iPad で運用するなら実機で確かめる価値がある。

## D. 【バグ】トーストが 1 個しかなく、後から出たものが前を消す

`toast()` は `$('toast')` という **単一要素**の `textContent` を上書きする（`app.js:119`）。

- エラーを出した直後に成功メッセージを出すと、**エラーが読まれる前に消える**（→ 問題 C が実際にこれ）
- 「戻す」ボタン付きのトースト（厨房の「用意した」）も、次のトーストが来た瞬間に
  ボタンごと消える。**押し間違いを取り消す唯一の導線が、無関係な通知で失われる**
- `clearTimeout(toastT)` で前のタイマーも消えるので、2 件目の表示時間だけが効く

厨房は「用意した」を連打する画面なので、2 件続けて押すと 1 件目の「戻す」は必ず消える。

## E. 【設計】営業回を切り替えると、在庫が満タンに戻ったことになる

**確認した計算**

- `remainingOf` = `stock`（`config/limits/stock` の固定値）− `soldOf`（**いまの営業回だけ**を集計）
- 営業回を切り替えると `soldOf` が 0 になる → `remaining` が `stock` に戻る

物理的な在庫は 1 個も戻っていないのに、画面は「この先あと 100 カップ売れます」と言う。
厨房の焼き足し判断もこの数字を見ている。

確認ダイアログには「売上・在庫・番号札の集計が 0 から始まります」とあるが、
これを「在庫が満タン扱いに戻る」と読み取れる人は少ない。
午前の部 → 午後の部のような使い方をすると、そのまま売り切れ検知が効かなくなる。

**直すなら**: 営業回の切替時に在庫を入力し直させる、または `stock` を営業回ごとに持つ。

## F. 【設計】WASM が落ちると、記録表の状態変更ボタンが無言で全部消える

`transitionButtons()` は `window.goNextStatuses` が無ければ **空文字列を返す**（`app.js:1136`）。
記録表の各行から「用意した」「渡した」「中止」などが全部消え、
残るのは「支払い受取 / 未払いに戻す」だけになる。

売上と CSV は「集計を準備しています」という断りが出る（`renderFigures`）のに、
ここだけ何も言わずにボタンが消える。原因が画面から分からない。

なお受付は `lib/pure.js` の `fallbackBuild` で動き続けるので、
**注文は取れるが記録表から一切動かせない**という状態になる。

## G. 【設計】番号札の重複と在庫の二重引き当ては、クライアント側でしか防いでいない

これはコード中のコメントで既に自覚・許容されている（`app.js:541`）ので新発見ではないが、
場合分けの一覧としては挙げておく。

`placeOrder` は確定直前にサーバーの現在値を読み直して窓を縮めているが、
**読んでから書くまでの間は残る**。受付が 2 台あると、
「最後の 1 カップを両方が売る」「同じ札を両方が出す」が原理的に起こりうる。

`database.rules.json` 側にも札の重複を止める規則はない（RTDB のルールでは書きにくい）。

コメントは「文化祭の規模では窓を縮めるほうが割に合う」と判断理由まで書いてあるので、
**このまま行くなら、起きたときの直し方**（記録表から中止 → 取り直す）を
運用手順に書いておくのが現実的。

## H. 【小】通知音のスイッチが厨房タブにしかない

`<input id="sound">` は `#view-kitchen` の中にしかない（`index.html:883`）。
`soundOn()` は `$('sound').checked` を見るので判定は全画面で効くが、
**切り替えられるのは厨房タブを開いたときだけ**。

呼び出し表示や金額表示の端末で音を止めたいとき、いったん厨房タブに移る必要がある。
お客様に向けた端末でナビを開かせることになる。
